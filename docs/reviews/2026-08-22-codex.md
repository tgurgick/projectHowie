# Current Code Review

**Review date:** 2026-08-22  
**Scope:** Current repository state, runtime behavior, data-boundary implementation, agent/MCP interfaces, UI, simulations, and evaluation methods.

## Executive summary

The codebase is functional and the current test suite is green: **51 tests passed**, with one dependency deprecation warning. Compilation and whitespace checks also pass.

However, the project is not yet production-ready for the stated data-ownership boundary. The largest remaining issue is architectural: the system intends to use derived strategy context only, but several actual code paths can still expose raw scraped data to models, MCP clients, packages, or the browser.

The foundation is substantially better than the earlier version. The main work now is to make the privacy boundary enforceable in code, make the context artifact genuinely self-sufficient, and strengthen state, cache, UI, and evaluation reliability.

## Prioritized findings

### 1. Raw scraped data can still leave the system — P0

`howie3/agent.py` exposes arbitrary database querying through the `query_database` tool. Player context can include projections, ADP, weekly history, and other detailed records.

`howie3/mcp_server.py` exposes `player_card`, which returns detailed player data through `howie3/service.py`.

The system prompt says not to reproduce raw data, but a prompt is not a technical data boundary. Tool results are still sent into the model context.

#### Recommended change

Split local-only data access from model-facing tools. Remote/model-facing tools should return only approved abstractions, such as:

- player tiers and rankings;
- projected ranges and uncertainty summaries;
- simulation results and distribution summaries;
- roster marginal value;
- draft recommendations and strategy explanations;
- aggregated, non-reversible context features.

Remove arbitrary SQL and detailed game-log access from external interfaces. Add an egress test that invokes every agent/MCP tool and asserts that raw fields such as `weekly_stats`, `pass_yards`, `games`, and source records cannot cross the boundary.

Relevant files:

- `howie3/agent.py:153`
- `howie3/mcp_server.py:43`
- `howie3/service.py:390`

### 2. Packaging can accidentally ship raw data and credentials — P0

`MANIFEST.in` includes database files, pickle files, JSON files, and `.env`. `setup.py` also packages database artifacts.

This means a build can include raw scraped data or credentials if those files exist locally, even if they are not committed to Git.

#### Recommended change

- Remove raw-data and `.env` patterns from `MANIFEST.in`.
- Remove database and pickle patterns from `package_data`.
- Explicitly allowlist package assets.
- Add a build test that scans wheels and source distributions for databases, scraped JSON, pickle files, and secrets.
- Keep raw data in local ignored directories only.

Relevant files:

- `MANIFEST.in:4`
- `setup.py:73`

### 3. The context artifact does not yet power context-only simulation — P1

`howie3/context_artifact.py` exports simulation outcomes, but `load_context()` reconstructs only player projection, ADP, standard deviation, and bye-week data. The exported outcomes and availability information are discarded.

Context-only mode then sets simulations to zero in `howie3/views.py`. As a result, the tool falls back to deterministic projection and ADP rankings instead of using the exported strategy context.

#### Recommended change

Make the context artifact a portable derived-strategy bundle containing, at minimum:

- player identity and position;
- tier and ranking;
- projection range and uncertainty;
- availability or injury-state probabilities;
- simulation distribution summaries;
- roster marginal values;
- strategy-specific rankings and constraints;
- provenance metadata and schema version.

The artifact should allow the tool to operate without access to the raw database.

Relevant files:

- `howie3/context_artifact.py:80`
- `howie3/context_artifact.py:155`
- `howie3/views.py:195`

### 4. Strategy changes can leave stale recommendations — P1

`howie3/server.py` currently generates cache keys using a timestamp/seed/event-count combination. Changing strategy rules or notes does not necessarily change the generation key.

The UI can therefore continue showing recommendations generated before the user changed the strategy.

#### Recommended change

Include all recommendation inputs in the cache key:

- strategy-rule hash;
- league-settings hash;
- context-artifact version/hash;
- data schema version;
- simulation seed and repetition count;
- draft-state version.

Also avoid process-global caches when multiple settings or server instances may coexist.

Relevant file:

- `howie3/server.py:29`

### 5. Draft state validation is too permissive — P1

`howie3/state.py` primarily checks whether a player has already been selected. It does not comprehensively validate:

- pick number;
- team bounds;
- roster limits;
- draft completion;
- malformed state files;
- turn legality;
- conflicting writes.

This allows invalid or impossible draft states to be persisted or used for recommendations.

#### Recommended change

Add schema validation and explicit draft invariants before accepting or saving a pick. Reject invalid transitions with structured errors and make state loading fail safely when the file is malformed or incompatible with the current schema.

Relevant file:

- `howie3/state.py:107`

### 6. The UI has a broad injection surface — P1

`howie3/ui/index.html` contains many raw `innerHTML` interpolations for player names, research facts, SQL results, graph facts, and model output.

Imported research and model-produced text must be treated as untrusted, even on a localhost-only application.

#### Recommended change

- Prefer `textContent` and DOM construction over `innerHTML`.
- Centralize escaping for any unavoidable HTML rendering.
- Remove inline event handlers where practical.
- Add a restrictive Content Security Policy where possible.
- Add regression tests for malicious player names, research facts, and model suggestions.

Relevant file:

- `howie3/ui/index.html:523`

### 7. Traded-player graph facts can be incorrect — P1

`howie3/graph.py` groups data by player and team, then stores the result by player ID. For a traded player, the final row can overwrite the earlier row, making the result dependent on query ordering.

This can corrupt vacated-volume and room-share facts.

#### Recommended change

Aggregate across teams or select a team using an explicit deterministic rule, such as the team with the largest relevant volume. Add a regression test for a player traded mid-season.

Relevant file:

- `howie3/graph.py:118`

### 8. Evaluation evidence is not yet strong enough for expert claims — P1

The evaluation code depends on a legacy local database and defaults to only three repetitions. A result such as “Howie +48 vs ADP” should currently be treated as exploratory rather than conclusive.

#### Recommended change

Upgrade the evaluation framework to include:

- multiple historical seasons;
- paired seeds and matched draft conditions;
- substantially more repetitions;
- bootstrap confidence intervals;
- out-of-sample evaluation;
- ablation tests for each domain feature;
- comparison against several baselines, not only ADP;
- normalized derived inputs instead of a legacy database dependency.

Relevant files:

- `howie3/evals.py:53`
- `howie3/cli.py:218`

### 9. Static typing has regressed — P2

`mypy` currently reports errors across graph construction, roster valuation, simulations, service payloads, server state, MCP responses, and evaluation code.

The most concerning errors involve simulation result types and mismatches between service and MCP payload structures. Runtime tests pass today, but these errors increase the risk of regressions as the architecture evolves.

#### Recommended change

- Define shared typed models for simulation summaries and API/MCP payloads.
- Replace invalid tuple annotations with `Tuple[...]` or modern tuple syntax.
- Add explicit types to dynamic dictionaries.
- Fix optional-value handling at source boundaries.
- Make CI fail on new type errors, then reduce the existing baseline incrementally.

## Additional concerns

### Localhost is not a complete security boundary

The expanded server includes configuration writes, research execution, insights generation, simulation imports, and agent requests. These routes do not appear to have strong authentication, request-size limits, or origin/CSRF protections.

For a local desktop tool, this may be acceptable during development, but expensive or mutating endpoints should still use a random session token, strict request-size limits, and explicit confirmation where appropriate.

### Model egress paths should share one redaction policy

The agent path is not the only model egress path. `howie3/insights.py` sends arbitrary payload data to the model as well. All model calls should pass through the same approved-context serializer rather than each feature deciding independently what data is safe.

Relevant file:

- `howie3/insights.py:86`

### Local research artifacts need an explicit Git policy

`research/DAL.json` is currently untracked but not ignored. A normal `git add .` could stage it.

Because the project intentionally avoids committing scraped or ownership-sensitive data, local research directories should be explicitly ignored, and the repository should document which derived artifacts are safe to commit.

## Recommended implementation order

1. Enforce the raw-data egress boundary for agent, MCP, insights, and any other model-facing path.
2. Redesign the context artifact so it can power the tool without the raw database.
3. Remove raw data and credentials from package manifests and add artifact scanning tests.
4. Add cache versioning based on strategy, settings, context, and state.
5. Add comprehensive draft-state validation.
6. Remove unsafe UI interpolation and add injection regression tests.
7. Fix traded-player graph aggregation.
8. Upgrade the evaluation methodology and baselines.
9. Establish shared typed payload models and reduce the `mypy` error baseline.

## Overall assessment

The current code is in good shape as an active prototype: it runs, the test suite is green, and the system has a useful separation between service, simulation, agent, MCP, and UI layers.

The project should not yet be treated as a safe distributable tool because the raw-data boundary is policy-based rather than enforced. Once model-facing interfaces return only derived strategy context, the context artifact becomes self-sufficient, and packaging is locked down, the remaining issues become normal reliability and product-quality work rather than fundamental architectural risk.
